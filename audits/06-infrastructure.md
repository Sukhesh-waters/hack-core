### Findings
- [CRITICAL] Meta sync path has no dedup — duplicates the baseline every run — `src/app/(app)/w/[ws]/accounts/sync.ts:26-55` — `runAccountSync` calls `pullMetaMedia` (always returns the account's latest ~50 media items, `lib/connectors/meta.ts:60` `limit=50`, no "since last pull" cursor) and feeds every row straight into `buildImportPlan` → `INSERT posts` with zero dedup against existing `posts.externalId`. The `posts` table (`src/db/schema.ts:358-393`) has no unique constraint on `(workspaceId, externalId)` — only non-unique indexes on `workspaceId`/`clientId`/`source`. Contrast with `addPublicPage`, which this session correctly added `listExistingExternalIds`/`dedupeItems` to before inserting into `pattern_posts`. The Meta first-party path got no equivalent treatment. Concrete failure: with the hourly cron now live, every connected account re-imports its latest ~50 posts every hour. Each tick inserts full duplicate rows (same externalId, new `id`), which (a) multiplies `posts` table growth unboundedly, (b) re-embeds captions every hour (`embedPosts`, cost/perf), and worst, (c) `buildImportPlan` folds `incoming` engagement rates into the `baseline` array it computes scores against (`lib/import-pipeline.ts:32-40`) — so the statistical baseline itself becomes increasingly dominated by N duplicate copies of the same posts, skewing z-scores/magnitude for every future scoring pass. This directly contradicts the "syncs stay fresh automatically" claim in the cron's own doc comment, since "fresh" here means "corrupt."
- [HIGH] Dead Inngest trigger — `src/inngest/functions/account-sync.ts:60` — function listens for event `"accounts/sync.requested"` but nothing in the codebase ever calls `inngest.send({ name: "accounts/sync.requested" })` (confirmed via repo-wide grep). Harmless dead code today, but implies a manual-trigger UX was planned/expected and silently doesn't exist — the "Sync now" button goes through the server action directly, not through this event, so the two sync paths (cron and manual) never share Inngest's step/retry/observability infra despite `runAccountSync` being written to be shared.
- [MEDIUM] Cron sweep is not workspace-scoped and has no per-workspace fairness — `src/inngest/functions/account-sync.ts:29-32` — `syncAllConnectedAccounts` selects every `connected_accounts` row with `status='connected'` across ALL workspaces/orgs in one loop, sequentially awaiting `runAccountSync` for each. There's no batching/concurrency limit and no cap, so a large fleet makes each hourly tick's wall-clock time grow linearly with total connected accounts platform-wide, risking the Inngest step timeout. Workspace isolation is preserved for the actual DB writes (each `runAccountSync` call passes the account's own `workspaceId`), so this is an operational/scale risk, not a data-isolation bug.
- [LOW] `syncAccount` (manual) checks `metaConnectorEnabled()` before running, but the cron's `syncAllConnectedAccounts` also independently checks the same flag (`account-sync.ts:25`) — consistent today but the flag check is duplicated in three places (`accounts/page.tsx`, `accounts/actions.ts:54`, `account-sync.ts:25`) with no shared guard helper; a future change to the flag's semantics needs to be mirrored in all three.
- [LOW] `updateHeartbeat` status enum (`connected|error|disconnected`) has no "syncing" state, so a long-running sync (either manual or cron) is invisible to the UI/other workspace members until it finishes — not a correctness bug, just no in-flight indicator.

### Findings
- [MEDIUM] Import job can be permanently stuck at `status="processing"` on hard failures — `src/app/(app)/w/[ws]/clients/[clientId]/import/actions.ts:79-91` — the `status="failed"` update only runs inside the `catch` block of the same request; if the Node process is killed, times out at the platform/proxy level, or the request is aborted mid-await (e.g., serverless function timeout during `normalizeCaptions`/embedding), the job row is left at its default `processing` status forever with no retry/cleanup job to sweep stale entries. There's no `updatedAt`/heartbeat field on `importJobs` to detect staleness either, so the KB/import history UI (if any renders job status) has no way to distinguish "still running" from "abandoned."
- [LOW] `source="first_party"` tagging verified correct — `src/lib/import-pipeline.ts:52` hardcodes `source: "first_party" as const` for every row `buildImportPlan` produces, used identically by both the manual CSV path and the Meta connector sync path. Matches the two-layer constitution (first-party vs. pattern/public never mix). No bug.
- [LOW] Client name/handle validation is thin — `clientWithContextSchema` (`src/lib/validation.ts:126-136`) only requires `name` 2-60 chars; `handle` is fully optional/unvalidated (no `@`/format check, unlike `publicPageSchema`'s strict handle regex used for the pattern layer). A client can be created with a garbage-formatted "handle" string that later fails to match anything meaningful downstream (e.g., if any feature tries to reconcile client.handle against a real Instagram handle). Not a security issue, just weak input hygiene versus the stricter pattern used elsewhere in the same file.
- [LOW] Wizard step validation (`wizard.tsx:118-139`) is client-side-only gatekeeping for UX (step 0 name length, step 1 brandType/mission/showcaseTheme); the actual server-side `clientWithContextSchema` re-validates independently on submit, so a manipulated client bypassing the wizard's `next()` gate still gets caught server-side — no vulnerability, just noting the duplication is correct/expected defense-in-depth, not a flaw.
