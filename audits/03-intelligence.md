- [Medium] Citation allow-list uses the full driver pool, not the LLM-cited subset — `src/lib/ai/retrieval.ts:78-86` computes `citedPostIds` (drivers the brief actually referenced via `[xxxxxxxx]` markers) but `runIdeation` (`ideation/actions.ts:82`) never passes `retrieval.citedPostIds` into `generateIdeas`; it passes the full `retrieval.drivers` array, and `generateIdeas` → `validateCitations` (`ideation-agent.ts:110`) validates the ideation model's citations against `input.drivers.map(d => d.id)` (the entire driver pool: similar + top 5 up-movers + top 3 down-movers), not the subset the brief actually cited. Net effect: an idea's "why" can cite a first-party post that was in the retrieval pool but was never actually referenced in the driver brief the ideation model was grounded on — the citation is real first-party data (source stays first-party-only, so the two-layer rule itself is not violated), but the traceability chain from "why" reason → the evidence that produced it is weaker than the code's own naming (`citedPostIds`) implies. Concrete scenario: driver brief cites only 3 of 13 pooled drivers in its prose; ideation model is still free to attach any of the 13 driver ids as a citation on an idea, producing a "why" whose citation was never actually part of the analytical brief that grounded it.
- [Low] `getPostsByIds` doesn't re-assert `source="first_party"` at read time — `src/db/queries/posts.ts:129-135` and used in `ideation/page.tsx:25` to resolve citation captions for display. But `getPostsByIds` has no defense-in-depth: if any future write path ever puts a pattern-layer post id into `ideas.citations`, this query will happily resolve and display it as if first-party, silently violating the two-layer rule at render time with no guard to catch it.

- [Info] Status transition `new → drafted` is guarded against races: `acceptIdea` re-checks `idea.status !== "new"` (`accept-idea.ts:32`) before generating a draft, and `markIdeaDrafted`/`rejectIdea`/`updateIdeaFields` (`db/queries/ideas.ts`) all additionally guard their `UPDATE` `WHERE` clause on `status="new"` (except `markIdeaDrafted`, see below), so a double-submit of "Draft it" cannot double-process an idea past the read-check window in the common case.
- [Low] `markIdeaDrafted`'s UPDATE is not itself guarded by `status="new"` — `src/db/queries/ideas.ts:33-36` — unlike `rejectIdea`/`updateIdeaFields`, which guard their `WHERE` with `eq(ideas.status, "new")`, `markIdeaDrafted` only filters by `workspaceId`+`id`.
