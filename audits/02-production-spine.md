### Findings
- [MEDIUM] Silent no-op on stale stage transition (race condition) — `src/db/queries/production.ts:70-84` — The guard-in-WHERE (`eq(content.productionStage, input.from)`) correctly prevents illegal double-transitions, but the UPDATE's affected-row count is never checked. If two users concurrently drag the same card (or a user double-clicks/has a stale page open), the second `advanceStage` call matches 0 rows, doesn't throw, and `advanceProductionStageAction` returns `undefined` (success) with a `revalidatePath`. The user sees the click "succeed" with no error, but the card doesn't move — confusing silent failure rather than a clear "someone already moved this card" message. No `production.test.ts` exists to cover this.
- [LOW] Card has no assignee field, but "Unassigned" badge is hardcoded and non-interactive — `src/app/(app)/w/[ws]/production/production-card.tsx:100-103` — Dead visual element; no assignment action exists anywhere in production/actions.ts. Not a regression from this session, but worth flagging as a dead-end UI affordance (badge implies a feature that isn't wired).
- [LOW] `createProductionCardAction` doesn't revalidate `/calendar` or `/studio` — `src/app/(app)/w/[ws]/production/actions.ts:76` — Not a bug in practice (those pages are `force-dynamic` and re-fetch on navigation), but noted for completeness since the sibling calendar action has the same asymmetry.

### Findings
- [CRITICAL] Direct-add content from Production/Calendar can never reach Approvals — no path exists to populate `content.body` for cards created via `createProductionCard` or `createScheduledPost` — `src/db/queries/production.ts:40-56`, `src/db/queries/schedule.ts:119-145`, `src/app/(app)/w/[ws]/studio/[contentId]/actions.ts:139-141` (compliance) and `:35-36` (refine) — Both direct-add paths insert `body: ""`. The Studio's `runComplianceAction` requires `row?.body` truthy and `parseDraftBody(row.body)` to return non-null (fails on empty string → `parseDraftBody` needs `## Caption/## Script/## Hashtags/## CTA` sections); `refineDraftAction` has the identical `if (!row?.body)` guard. There is no manual body-editing UI anywhere in the app (grepped: no body-write action outside studio's AI-only paths). **Concrete failure**: a user adds a card via Production's "New card" button or Calendar's "Add to this day" form, clicks through to the Studio draft page, clicks "Run compliance" — gets the error "This content isn't a structured draft." with no recovery action. The card is permanently stuck at `status:"draft"`, `complianceStatus:"pending"`, and can never appear in Approvals' queue (`status IN (review, approved)`), never reach `scheduleContent`, and never get `status:"scheduled"`. This is a genuine orphan, not merely a UX rough edge — the compliance gate closure (this session's stated goal) works correctly for content that *has* a body (i.e., content from `acceptIdea`), but it collaterally strands all content from the two newly-added quick-add entry points, since neither entry point generates or otherwise supplies draft content.
- [LOW] `ApproveForm`/`ScheduleForm` re-validate membership+ownership per submit (defense in depth, consistent with rest of codebase) — no issue, noted only because it's the one place a double-DB-round-trip pattern is deliberate and correct.

### Recent draft-first change verification
The three changes described (draft-first `createScheduledPost`, color-coding via `src/lib/colors.ts`, `isPendingStatus` badge in `calendar-board.tsx`) are **internally coherent but not end-to-end coherent** with the rest of the pipeline:
- **Compliance-bypass closure**: verified correct in isolation. `createScheduledPost` no longer writes `status:"scheduled"` directly; it writes `status:"draft"`+`productionStage:"brief"`, matching `createProductionCard`'s pattern. Grepped every writer of `content.status = "scheduled"` — only `scheduleContent` (schedule.ts:158) does this, and it's only reachable via `approveAction`'s `complianceStatus === "passed"` gate. The bypass is genuinely closed.
- **`isPendingStatus` badge**: correctly implemented and wired — `calendar-board.tsx:39-41` classifies `draft`/`review` as pending, both the month-grid chip color (`chipClasses`, :43-50) and the day-panel "Pending approval" badge (:174-180) use it consistently. No dead code here.
- **The gap**: the new flow assumes calendar-created drafts will "surface correctly in Production/Approvals so it can be pushed forward" (per this task's own framing) — Production is fine (`listProductionQueue` picks up any row with non-null `productionStage`, so the card **does** appear on the Production kanban and **can** be dragged through `brief → in_progress → internal_review → done`). But **Approvals never sees it**, because Approvals' queue is keyed on `content.status IN (review, approved)`, and nothing advances `status` off `"draft"` except the Studio's `runComplianceAction`, which requires a real AI-generated draft body that quick-added cards never get. So the slot **does** show up correctly colored/badged on the calendar itself (visually correct, not orphaned from the calendar's own rendering), but the underlying content record is an operational dead end — it can be marked "done" on the Production board while still sitting at `status:"draft"` forever, and the calendar chip will show "Pending approval" permanently since there is no way to move it past `draft`/`review`. The fix that closed the security bypass is correct, but it exposed a pre-existing missing link (no body-generation entry point for directly-created cards) that the constitution's degradation ladder doesn't address, since this isn't a provider-outage scenario — it's a straight missing feature/action.

- Top 3 by impact:
  1. **Orphaned direct-add content** (Critical) — `createProductionCard` and `createScheduledPost` both create `body:""` content with no downstream way to populate a real draft, so anything added via Production's "New card" or Calendar's "Add to this day" can never pass compliance, never reach Approvals, and never get scheduled.
